# Задание 1 — Архитектура «Будущее 2.0» (целевое состояние через год)

---

## Часть 1. Диаграмма контейнеров C4 (PlantUML)

Файл с диаграммой: `architecture_c4.puml`

### Ключевые архитектурные решения

| Решение | Обоснование |
|---|---|
| Переход в облако (Cloud DWH — Snowflake / Azure Synapse) | Заменяет устаревший SQL Server 2008; горизонтальное масштабирование, быстрые аналитические запросы |
| Разделение на домены (Medical, Fintech, AI, Corporate) | Независимое развитие направлений, соответствие регуляторным требованиям (медицинские ≠ финансовые данные) |
| Event Streaming (Apache Kafka / Azure Event Hub) | Заменяет устаревший ESB; асинхронная интеграция, лёгкое подключение новых бизнесов |
| Портал самообслуживания (Self-Service Data Portal) | Прямой доступ аналитиков к данным без участия IT |
| Отказ от PowerBuilder → современный Web-UI | Нет доступных разработчиков PowerBuilder; снижение bus-factor |
| Медицинские карты остаются в изолированном домене | Требования HIPAA / 152-ФЗ; медданные не попадают в общую аналитику |

### Как архитектура поддерживает бизнес-сценарии

| Бизнес-сценарий | Как поддерживается в целевой архитектуре |
|---|---|
| **Быстрая подготовка отчётности** | Cloud DWH с колоночным хранением + ELT-пайплайны через Airflow; запросы на сотнях ТБ — секунды/минуты вместо часов |
| **Независимое развитие финтех и ИИ** | Каждый домен — своя среда, своя БД, свой CI/CD; изменения в медицинском домене не ломают финтех |
| **Масштабирование для новых бизнесов** | Новая фармкомпания или производитель оборудования подключается через Kafka-топик и регистрирует свой домен; общая аналитика не требует переписывания DWH |
| **Портал самообслуживания** | Сотрудник выбирает срезы в веб-интерфейсе → запрос идёт прямо в Cloud DWH → ответ в секунды |
| **Управленческие решения без задержек** | Отчётность актуальна (near-realtime через Kafka), не требует ночных batch-запусков |

## Часть 2. Проблемные места текущей архитектуры

| # | Проблема | Описание | Пострадавшие бизнес-сценарии |
|---|---|---|---|
| P1 | **Монолитный DWH (SQL Server 2008)** | Вся бизнес-логика, все данные, все трансформации — в одном месте. Версия 2008 снята с поддержки Microsoft. Нет секционирования, колоночного хранения, нет горизонтального масштабирования | Быстрая отчётность, подключение новых бизнесов, безопасность (нет патчей) |
| P2 | **Медленное формирование отчётов (часы)** | Сотни ТБ данных + сотни трансформаций в одном DWH = конкурентные запросы блокируют друг друга. Формирование сложных отчётов занимает часы | Управленческие решения, операционная аналитика, согласование с банком-дочкой |
| P3 | **Отсутствие доменного разделения данных** | Медицинские, финансовые, кадровые данные лежат в одном хранилище. Разграничение доступа реализовано кастомными скриптами, не масштабируется | Соответствие 152-ФЗ / HIPAA, независимость развития финтех и медицины |
| P4 | **ESB как единая точка интеграции и отказа** | Apache Camel в монолитной конфигурации — добавить новый источник/потребитель данных требует изменения ESB-конфигурации и координации всех команд | Подключение фармкомпаний, масштабирование ИИ-сервисов, time-to-market |
| P5 | **PowerBuilder — legacy UI** | Технология 1990-х годов, крайне мало специалистов на рынке. Любые доработки UI медленны и дороги | Эффективность операторов клиник, time-to-market новых функций |
| P6 | **BI-система с тяжёлыми кастомизациями поверх DWH** | Power BI настроен прямо поверх DWH-структур. Любая миграция DWH требует переработки всех отчётов — блокирует трансформацию | Быстрая отчётность, любая миграция инфраструктуры |
| P7 | **Нет портала самообслуживания** | Каждый аналитический запрос требует участия IT-команды, которая пишет запрос к DWH. Это создаёт очередь и зависимость бизнеса от IT | Операционная и управленческая аналитика, финтех-отчётность |
| P8 | **Отсутствие изолированной среды для ИИ** | ИИ-сервисы обращаются к медицинским данным через ESB без governance-слоя. Нет версионирования моделей, аудита | Регуляторные требования, качество медицинских сервисов |
| P9 | **Нет готовности к подключению новых бизнесов** | Чтобы интегрировать фармкомпанию или производителя оборудования, нужно добавлять коннекторы в ESB и схемы в DWH — трудоёмкий процесс | Масштабирование экосистемы, стратегия роста компании |

## Часть 3. Приоритизация проблем (MoSCoW)

### Связь с бизнес-целями

| Бизнес-цель | Влияние на приоритизацию |
|---|---|
| **Выручка** | Быстрый выход финтех-продуктов на рынок (P4, P9), скорость принятия решений (P2, P7) |
| **Time-to-market** | Независимость команд (P3, P4), снижение зависимости от DWH (P1, P6) |
| **Качество медицинских сервисов** | ИИ-диагностика без задержек (P8), надёжность медицинской системы (P1) |
| **Качество финансовых сервисов** | Изоляция финтех-домена (P3), регуляторное соответствие (P3, P8) |
| **Регуляторное соответствие** | Разделение медицинских и финансовых данных (P3), патчи безопасности (P1) |

### MoSCoW

#### MUST HAVE — критично, без этого цели через год не достижимы

| Проблема | Почему Must Have | Действие |
|---|---|---|
| **P1** — Монолитный DWH 2008 | Критический риск безопасности (нет патчей), блокирует масштабирование; всё остальное строится поверх | Мигрировать на Cloud DWH (Snowflake или Azure Synapse) |
| **P2** — Медленная отчётность | Напрямую бьёт по выручке: задержка управленческих решений на несколько часов = упущенные возможности | Перейти на ELT + колоночное хранилище, Airflow для оркестрации |
| **P3** — Нет доменного разделения | Регуляторный риск (152-ФЗ, банковская лицензия). Штрафы и отзыв лицензии = потеря бизнеса | Выделить домены: Medical, Fintech, Corporate; физически изолировать данные |
| **P7** — Нет портала самообслуживания | Это прямая цель бизнеса на год, поставленная руководством | Построить Self-Service Data Portal поверх Cloud DWH |

#### SHOULD HAVE — важно, влияет на скорость и качество

| Проблема | Почему Should Have | Действие |
|---|---|---|
| **P4** — ESB как узкое место | Блокирует подключение новых бизнесов (фармкомпании), но ESB пока работает — есть время мигрировать постепенно | Внедрить Kafka, мигрировать потоки событий по доменам |
| **P6** — BI поверх DWH | Тормозит миграцию DWH, но можно выполнить параллельно с P1 — сначала создать промежуточный слой данных | Создать семантический слой / data mart между DWH и BI |
| **P8** — ИИ без governance | Важно для качества и регуляторов, но ИИ-сервисы сейчас работают — риск не моментальный | Добавить API-шлюз для медданных, MLflow для версионирования моделей |

#### COULD HAVE — желательно, но не блокирует год

| Проблема | Почему Could Have | Действие |
|---|---|---|
| **P5** — PowerBuilder legacy UI | Операторы работают, хотя и с неудобствами. Замена UI — отдельный проект, не влияет на аналитику | Запланировать замену на современный Web-UI в следующем цикле |
| **P9** — Нет готовности к новым бизнесам | Фармкомпании и производители оборудования — ближайшие планы, но не критично к году, если Kafka уже есть | После внедрения Kafka подключение станет декларативным |

#### WON'T HAVE (сейчас) — откладываем

| Проблема | Обоснование |
|---|---|
| Полная замена всех финтех-сервисов | Сервисы работают и приносят выручку; рефакторинг без необходимости несёт риск |
| Полный data mesh со всеми доменами | На год достаточно «Data Mesh lite» — выделить домены, но не требовать полной автономии каждого |
