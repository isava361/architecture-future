# Задание 2 — Доменное разделение и потоки данных «Будущее 2.0»

---

## Часть 1. Разделение системы на домены

### Принципы разделения

Домены выделены по бизнес-способностям, а не по техническим слоям.
Каждый домен:
- принадлежит одной команде и одному подразделению;
- владеет своими данными и своей БД (нет прямого доступа к чужим таблицам);
- общается с другими доменами только через **события (Kafka)** или **API-контракты**;
- может деплоиться, масштабироваться и развиваться **независимо**.

Это напрямую решает ключевую проблему — необходимость внедрять новую логику в монолитный DWH.

---

### Карта доменов

| # | Домен | Команда-владелец | Bounded context | Ключевые данные | Регуляторные ограничения |
|---|---|---|---|---|---|
| 1 | **Медицинский** | Клиники | Пациенты, приёмы, диагностика, лечение | Медкарты, снимки, истории болезни, анализы | 152-ФЗ (ПДн), медицинская тайна |
| 2 | **ИИ** | ИИ-компания | ML-модели, автодиагностика, анализ изображений | Обезличенные медданные, ML-модели, результаты предсказаний | Работает только через одобренный Medical API, аудит доступа |
| 3 | **Финтех** | Банк | Банковские операции, кредиты, платежи, счета | Транзакции, счета, кредитные истории | ЦБ РФ, PCI-DSS, банковская тайна |
| 4 | **Корпоративная аналитика** | Головной офис | Консолидированная отчётность, KPI, управленческие дашборды | Агрегированные данные всех доменов (без сырых ПДн и медкарт) | Внутренняя политика доступа |
| 5 | **Партнёрский** | Партнёры + Integration Team | Фармацевтические данные, телеметрия медоборудования | Каталог препаратов, данные с устройств | Зависит от партнёра |

> Медкарты, снимки и истории болезни остаются **исключительно** в Медицинском домене. В Corporate DWH и портал самообслуживания они не попадают — только агрегированные статистические показатели без ПДн.

---

### Границы доменов и связи

```
┌────────────────────────────────────────────────────────────────────┐
│                     ИНТЕГРАЦИОННАЯ ШИНА (Kafka)                    │
│         Единственный канал асинхронной связи между доменами        │
└──────┬──────────────┬──────────────┬──────────────┬───────────────┘
       │              │              │              │
  [Медицинский]  [Финтех]       [ИИ]         [Партнёрский]
       │                                           │
       └──────────────────────────────────────────►│
                                                   ▼
                                      [Корпоративная аналитика]
                                       (собирает агрегаты)
```

Прямые синхронные связи (через API Gateway):
- Медицинский домен ↔ ИИ-домен (запрос диагностики — реального времени)
- Внешние клиенты → Финтех-домен (банковские операции)

Все остальные взаимодействия — **асинхронные через Kafka**.

### Описание потоков по сценариям

#### Сценарий А: ИИ-диагностика пациента

| Шаг | Откуда | Куда | Данные | Механизм |
|---|---|---|---|---|
| 1 | Оператор | Медицинская Web-система | Данные приёма, снимок | HTTPS |
| 2 | Медицинская система | Medical API | Запись данных пациента | REST |
| 3 | Medical API | Медицинское хранилище | Сохранение медкарты | SQL |
| 4 | Medical API | ИИ-платформа | Обезличенные данные + снимок (по согласию) | gRPC |
| 5 | ИИ-платформа | ML Registry | Загрузка актуальной модели | MLflow API |
| 6 | ИИ-платформа | Medical API | Результат диагностики (вероятность, рекомендации) | gRPC |
| 7 | Medical API | Медицинская система | Отображение диагноза оператору | REST |
| 8 | Medical API | Kafka | Событие: «Приём завершён» (без ПДн, с агрег. метриками) | Kafka Producer |

#### Сценарий Б: Интеграция нового финтех-сервиса (кредит пациенту)

| Шаг | Откуда | Куда | Данные | Механизм |
|---|---|---|---|---|
| 1 | Пациент | API Gateway | Запрос кредита на лечение | HTTPS/Mobile |
| 2 | API Gateway | Финтех-сервисы | Проксируется запрос | HTTPS |
| 3 | Финтех-сервисы | Финтех БД | Проверка кредитной истории | SQL |
| 4 | Финтех-сервисы | Финтех БД | Создание кредитной заявки | SQL |
| 5 | Финтех-сервисы | Kafka | Событие: «Кредит выдан» (сумма, категория) | Kafka Producer |
| 6 | Финтех-сервисы | Пациент | Подтверждение кредита | HTTPS/Mobile |
| 7 | Kafka | Airflow (Корп. аналитика) | Агрегированное финансовое событие | Kafka Consumer |
| 8 | Airflow | Corporate DWH | Обновление финансовых KPI | SQL Bulk Load |

> Новый финтех-продукт (страховка, рассрочка, BNPL) добавляется как новый микросервис внутри Финтех-домена. Другие домены не меняются — они видят только новые события в Kafka.

#### Сценарий В: Подключение новой фармкомпании (партнёра)

| Шаг | Откуда | Куда | Данные | Механизм |
|---|---|---|---|---|
| 1 | Фармкомпания | API Gateway (Partner API) | Каталог препаратов, обновления цен | HTTPS/EDI |
| 2 | Partner Gateway | Kafka (новый топик `pharma.catalog.v1`) | Структурированные данные о препаратах | Kafka Producer |
| 3 | Kafka | Медицинский домен (опционально) | Актуальные данные о препаратах для назначений | Kafka Consumer |
| 4 | Kafka | Corporate DWH через Airflow | Аналитика по использованию препаратов | Kafka Consumer |

> Подключение фармкомпании не требует изменений ни в Medical API, ни в Финтех-сервисах, ни в DWH-схеме. Создаётся только новый Kafka-топик и новый consumer в нужных доменах.

#### Сценарий Г: Быстрая подготовка управленческого отчёта

| Шаг | Откуда | Куда | Данные | Механизм |
|---|---|---|---|---|
| 1 | Менеджер | Портал самообслуживания | Запрос среза (период, домен, KPI) | HTTPS |
| 2 | Портал | Corporate DWH | SQL-запрос к предагрегированным таблицам | SQL |
| 3 | Corporate DWH | Портал | Результат выборки (секунды, не часы) | SQL ResultSet |
| 4 | Портал | Менеджер | Отчёт / интерактивный дашборд | HTTPS |

> Данные уже агрегированы и трансформированы в Cloud DWH через Airflow-пайплайны. Менеджер не ждёт batch-обработки — отчёт готов за секунды.

## Часть 3. Обоснование логики разделения на домены

### 3.1 Ускорение вывода продуктов на рынок (Time-to-market)

**Проблема «как было»:** Любое изменение логики — будь то новый финтех-продукт или новая ИИ-модель — требовало изменения схем и хранимых процедур в монолитном DWH. Это создавало очередь из нескольких команд к одному узлу.

**Как домены решают это:**

| Команда | До разделения | После разделения |
|---|---|---|
| Финтех | Согласование изменений DWH → 2–4 недели | Деплой внутри Финтех-домена → 1–3 дня |
| ИИ | Запрос данных через DWH → очередь, задержки | Прямой API к Medical Domain → часы |
| Клиники | Зависимость UI от DWH-структуры | Независимый деплой Medical Web-системы |
| Новый партнёр | Изменение схемы DWH → месяцы | Новый Kafka-топик → дни |

---

### 3.2 Снижение зависимости от DWH

Монолитный DWH — не просто хранилище данных в «Будущем 2.0», он является **единственной точкой**:
- операционных данных всех доменов,
- бизнес-логики всех направлений,
- интеграции через ESB,
- аналитики через BI.

После доменного разделения DWH трансформируется в **специализированный аналитический инструмент** (Corporate Cloud DWH), который:
- принимает только агрегированные события через Kafka,
- не содержит операционной логики,
- масштабируется независимо от операционных систем.

```
            ДО                              ПОСЛЕ
    ┌──────────────────┐          ┌────────┐  ┌────────┐
    │                  │          │Medical │  │Fintech │
    │   DWH-монолит    │          │  DB    │  │  DB    │
    │  (операции +     │   →      └────────┘  └────────┘
    │   аналитика +    │               │           │
    │   логика всего)  │            [Kafka]    [Kafka]
    └──────────────────┘               └─────┬─────┘
                                             ▼
                                    ┌─────────────────┐
                                    │  Corporate DWH  │
                                    │  (только аналит.)│
                                    └─────────────────┘
```

---

### 3.3 Возможность отдельного развития каждого направления

| Аспект | Медицинский домен | Финтех-домен | ИИ-домен |
|---|---|---|---|
| **Технологии** | Java + React, специфика EMR | Golang/Java, банковские стандарты | Python, ML-фреймворки |
| **Цикл релизов** | Медленный (регуляторное согласование) | Быстрый (конкурентный рынок) | Непрерывный (модели обновляются постоянно) |
| **Масштабирование** | По числу пациентов и клиник | По числу транзакций | По объёму обрабатываемых изображений |
| **Регулятор** | Минздрав / Роскомнадзор | ЦБ РФ | Нет прямого регулятора |
| **Инциденты** | Отказ не должен влиять на финтех | Отказ не должен влиять на приёмы | Деградация ≠ остановка клиники |

Изоляция доменов означает: **инцидент в одном домене не останавливает другие**.

---

### 3.4 Готовность к интеграции новых бизнесов

Текущая архитектура с ESB + монолитным DWH требует для подключения каждого нового бизнеса:
1. Разработки нового коннектора в ESB,
2. Изменения схемы DWH,
3. Обновления всех зависимых отчётов в BI.

После доменного разделения с Kafka:
1. Новый бизнес регистрирует **Kafka Producer** с оговорённой схемой (Avro/JSON Schema),
2. Заинтересованные домены подписываются на нужные топики,
3. Corporate DWH получает данные через уже существующий Airflow-пайплайн.

**Пример:** Подключение производителя медоборудования занимает **1–2 спринта** вместо нескольких месяцев.

---

### 3.5 Соответствие структуре команд (Закон Конвея)

Доменное разделение **совпадает с организационной структурой** «Будущего 2.0»:

| Организационное подразделение | Домен |
|---|---|
| Клиники | Медицинский домен |
| ИИ-компания | ИИ-домен |
| Банк | Финтех-домен |
| Головной офис | Корпоративная аналитика |
| Будущие партнёры | Партнёрский домен |

Каждая команда отвечает за «свой» домен целиком — от кода до данных. Это устраняет межкомандные зависимости и ускоряет принятие решений.

---

### Итог: почему именно такие домены?

| Домен | Обоснование выделения |
|---|---|
| **Медицинский** | Критичные ПДн и медтайна — строгая изоляция обязательна; отдельная команда (клиники); специфичный стек (EMR) |
| **ИИ** | Самостоятельная компания в экосистеме; потребляет медданные, но не владеет ими; непрерывный цикл обновления моделей |
| **Финтех** | Банковская лицензия — строгая регуляторная изоляция; быстрый рыночный цикл; собственная команда (банк) |
| **Корпоративная аналитика** | Консолидирует данные всех доменов для HQ; не имеет операционной логики; владелец — головной офис |
| **Партнёрский** | Изоляция внешних источников данных защищает ядро экосистемы; новые партнёры не должны требовать изменений в существующих доменах |
